## 4. Scaling Risks — Multi-School Architecture

### 🔴 RISK 1: RLS Policies Entirely Absent
**Severity: CRITICAL**  
All 9 migration files create tables, indexes, and `updated_at` triggers — but **zero** RLS policies (`CREATE POLICY`).  

**Implication**: The moment `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` is toggled on Supabase, all queries will be blocked. Without it, any authenticated user can read/write any school's data.

**Schema strength**: Every data table correctly includes `school_id` with foreign key references — the multi-tenant column pattern is in place.

**Required actions before production**:
1. `ALTER TABLE public.schools ENABLE ROW LEVEL SECURITY;` (and all child tables)
2. Policies like:
   ```sql
   CREATE POLICY "Users can view their own school's students"
     ON public.students FOR SELECT
     USING (school_id IN (
       SELECT school_id FROM public.profiles WHERE id = auth.uid()
     ));
   ```
3. `FOR ALL` policy for `super_admin` override
4. Separate migration file (migration 010) for all RLS policies

### 🟡 RISK 2: Offline Sync — No Conflict Resolution Strategy
**Severity: HIGH for production**  
The offline layer uses Dexie with a `sync_queue` pattern, which is correct for the foundation, but **missing critical components**:

- **No conflict resolution field**: `SyncQueueItem` tracks `attempts` and `last_error` but has no `conflict_strategy` or `server_version` field for last-write-wins or merge logic.
- **No resolution logic**: The sync client (not yet written) needs CRDT-style or timestamp-based conflict detection.
- **No UI for conflicts**: Users will have no way to see or resolve sync conflicts.
- **No sync status component**: No indicator showing "online/offline/syncing/conflicts".
- **Schema mismatch**: `SyncQueueItem.created_at` and `synced_at` are `TIMESTAMPTZ` on Supabase side, but `Date` on Dexie side — potential serialization issues.

**Recommended additions**:
- `sync_versions` table tracking `last_modified` per row
- `updated_at` in offline Dexie schema for conflict detection
- Exponential backoff for sync retry (currently just `attempts` counter)
- Sync health dashboard

### 🟡 RISK 3: PWA Install Flow — Stub Only
**Severity: HIGH for user adoption**  
`next-pwa` is listed in `package.json` but:

- **Not configured** in `next.config.js` — no `withPWA()` wrapper
- **No `manifest.json`** — app name, icons, theme color, display mode not defined
- **No service worker registration** — no offline caching strategy
- **`public/icons/` and `public/images/` are empty** — zero app icons
- **No install prompt handling** — no `beforeinstallprompt` event listener

## 5. Architecture Strengths (What's Done Well)

Despite the blockers, the architecture foundation is **solid**:

1. **Strong TypeScript types** — Entity interfaces are clean, well-named, and cover all core business objects.
2. **School-scoped schema** — Every data table has `school_id` with FK constraint. Multi-tenant data isolation is built into the schema.
3. **SQL migrations are methodical** — Numbered, idempotent (`IF NOT EXISTS`), with proper indexes and `updated_at` triggers.
4. **Offline-first DB layer** — Dexie schema mirrors the Supabase tables with proper indexes. Sync queue table exists on both sides.
5. **Dependency choices are solid** — React Query for server state, Zustand for client state, Zod for validation, Dexie for offline, Tailwind for styling.
6. **Seed trigger pattern** — Auto-creation of default categories on school creation is a good DX pattern.
7. **Financial summary views** — SQL views for aggregation, avoiding expensive client-side computation.
